# 전투 분석 · 시뮬레이션의 입력 — 무엇을 어디서 가져오나

목표(사용자, 2026-10-08): 세이브에서 읽은 파티로 **전투 분석 · 시뮬레이션**을 한다.
시뮬에 필요한 값은 세 곳에서 온다 — **세이브**(그 개체만의 값), **DB**(종 · 기술 · 특성의 공통 값, PokéAPI), **계산**(둘을 합쳐 만드는 값).
이 문서는 그 지도이고, 바이트 위치는 세대 문서(4세대: [gen4/pk4.md](gen4/pk4.md))를 가리킨다.

## 2. 세이브에 없는 것

| 값 | 어디서 | 비고 |
|---|---|---|
| 상대 파티(체육관 관장 · 라이벌 …) | 세이브에 없다 — ROM 데이터 | ROM은 읽지도 커밋하지도 않는다(CLAUDE.md §7). 공략 사전처럼 **사실을 구조화한 JSON**을 따로 만드는 길이 있다(ADR이 필요) |
| 배틀 중 상태(능력 랭크 · 날씨 · 필드 · 교체 기록) | 시뮬이 스스로 만든다 | 실제 진행 중 배틀을 읽으려면 라이브 메모리(overlay-design.md §3 B안)가 필요하다 |
| 타입 상성 | 앱이 이미 있다 | `core/types/typechart` (세대별) |
| 데미지 공식 · 랜덤 · 급소 | 세대별 규칙 | `core/rules`에 **데이터(표)**로 둔다 — `if (gen >= 5)` 분기 금지(CLAUDE.md §4). 공식은 시뮬 단계에서 출처를 대조해 별도 문서로 정리한다 |

## 3. 번호 변환이 필요한 칸 (세이브 번호 ≠ DB id)

| 칸 | 세이브의 번호 | DB로 가는 길 |
|---|---|---|
| 지닌 물건 · 가방 물건 | 4세대 게임 번호(예: 217 선제공격손톱, 328 기술머신01) | PokéAPI `item_game_indices`(generation_id = 4)의 `game_index` → `item_id` |
| 성격 | 게임 순서 0–24(0 노력 · 1 외로움 …) | PokéAPI `natures.game_index` → `id` |
| 폼 | 종 + 폼 번호 | 종별 폼 → `pokemon.id` 표 |
| 장소 | 게임 장소 번호(+ 3002 "먼 곳" 규칙) | 게임별 장소 표(전투와 무관) |

종 · 기술 · 특성 번호는 PokéAPI id와 **같아서** 변환이 없다. 이 변환들은 data 레이어(H2)의 일이다 — core는 DB를 모른다.

## 4. 시뮬을 시작할 때의 순서 (제안)

1. `ReadMember`에 ✗ 칸 추가(상태 이상 · PP · PP 업 · 성별 · 친밀도 · 경험치 · 6능력치) — 바이트 위치는 [gen4/pk4.md](gen4/pk4.md)
2. H2의 번호 변환(물건 · 성격 · 폼) → 시뮬 입력 구조체(종족값 · 타입 · 기술 데이터를 DB에서 채운 것)
3. 데미지 계산 한 줄(공격 1회)을 core에 표 기반으로 — 세대 규칙 표 · 테스트 값은 출처 대조 후
4. 그 위에 턴 진행 · 교체 · 확률 분포
